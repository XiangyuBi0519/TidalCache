当前问题
并发请求导致 P 节点卡死：发送 2+ 并发请求后，所有 16 个 worker 进入 _model_forward 后不再返回，约 5 分钟后 TimeoutError 崩溃。

排查过程与发现
定位卡死位置：通过在 model_runner_v1.py 加 [PCP-WORKER] 日志，确认 16 个 worker 全部卡在 _model_forward（模型前向计算内部），排除了调度、通信、KV 传输等外部原因。
分析 scheduler dump：多次崩溃的 dump 数据一致显示混合调度模式——新请求（num_computed_tokens=0）和正在运行的请求（num_computed_tokens=5531）被同时调度，总 token 刚好用满 budget=65536。
推测根因：混合调度触发 chunked context 路径（因为 max_context_len > 0），导致 _compute_prefill_context 中 NPU kernel npu_fused_infer_attention_score 收到的 actual_seq_lengths_kv 包含 0（新请求没有 context KV），而该请求仍有大量 query token，kernel 无法处理 query>0 但 KV=0 的情况。
编写修复补丁：在 _compute_prefill_context 中增加逻辑——检测到 per-request KV 长度含 0 时，过滤掉 KV=0 的请求单独处理（输出 zeros/-inf），只对有效请求调用 kernel。
验证修复：
部署补丁 + 清除 __pycache__ 和 torch_compile_cache → 仍卡住
加 --enforce-eager 跳过 ACL Graph 编译 → 仍卡住
说明卡死点可能不在 _compute_prefill_context，或不仅在此处
额外发现：之前加在 attention_cp.py 里的 debug 日志始终没有输出（logger.info 和 logger.error 均未打印），说明在卡死发生前，代码可能还没执行到该函数，真正的卡点可能在 forward_impl 更上游的位置。
下一步方案
在 forward_impl 的关键步骤间加 print(flush=True) 打点（共约 7 个点），覆盖：进入 chunked context 分支、allgather Q 启动、head attention 完成、context attention 完成、tail attention 完成等。通过观察最后一条打出的日志，精确定位卡在哪两个操作之间，然后针对性修复。
